# 同批次重复条目是自然工作流产物，并条收窄为同位无损合并

Dogfood 中发现同名同批次重复条目（脉动零糖白桃 ×2，同在客厅同到期日）。深挖真实使用动线后确认：**重复条目大概率是自然使用产物，不是数据错误**——

1. **同一批买的东西会分放不同位置**：客厅一瓶、厨房一瓶，录入时录的是"眼前这一瓶"的位置；
2. **录入时不知道家里实际总量**：用户不会为了把数量改成"全家共有几瓶"去翻记录清点，数量字段语义是"这个位置的这一份"；
3. **翻出已录过的东西时，扫码快填远快于搜索改数量**：翻箱倒柜找出一样的一瓶，顺手扫条码直接录入，比搜记录找出来改数量快得多——录入动线的效率优先于账面整洁。

## Considered Options

- 强合并（并条键不含位置）——**否决**：同批分放不同位置是真实物理状态，跨位置合并会丢位置信息
- 引导用户"搜索已有记录 → 改数量"代替重复录入——**否决**：比扫码直接录慢，违背上面第 3 条动线
- 只提示不自动合并（把整理负担还给用户）——**否决**：用户明确反馈"我希望做成一条"，整理应由系统完成
- **采用**：并条键 = 名称+位置+到期日+单位（位置在键内，跨位置永不合并）；合并仅在"无损"时发生（分类/备注/自定义字段完全一致，重复行不带独有信息，宁两条不丢数）；扫码/复购快填动线保持不变，合并是保存后的静默后台行为

## Consequences

- 新增入库命中同批次（同位同批）→ 数量求和并入现有记录；DB init 时对存量无损重复做一次并条
- **跨位置的重复条目是预期状态，不是脏数据**；后续统计/提醒/复购设计不得假设"一条记录 = 该物品全部库存"
- 用户录入习惯零改变：扫码还是照扫，快填还是照填，并条对用户无感（仅 toast 告知合并结果）
- 备份恢复按快照原样还原（不合并）；恢复后下次 init 的存量去重兜底
- 实现锚点：`model/Material.ets`（batchQuantitySum / isLosslessDuplicate）、`db/MaterialDb.ets`（findActiveBatchMatch / consolidateDuplicateBatches）、CONTEXT.md「同批次合并」
